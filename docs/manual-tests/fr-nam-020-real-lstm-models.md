# FR-NAM-020 manual test: real (not generated) LSTM models

**Requirement (literal):** Namir shall support, at minimum, the `WaveNet` and `LSTM` architectures
as published in the NAM model format. *Verify:* G — one model of each architecture compared against
reference output.

**Why this manual test exists, given FR-NAM-020 is already automated.** The automated half is real
and stands: `crates/namir-nam/src/lstm.rs` is parity-tested against an independent from-scratch
reference, per D-19.1 and the pattern D-9.11 generalises. But every LSTM model that test has ever
seen was **generated by `namir-fixtures`**, whose `LstmShape` doc comment explicitly disclaims its
dimensions as "not verified against any real NAM LSTM preset" — unlike `WaveNetShape::Standard`,
which is cited against the trainer's own `get_wavenet_config`. So the shapes we test are shapes we
invented.

That is exactly the gap `AGENTS.md` warns about, and it has bitten this project once already: the
post-M6 parser bug, where a real `.nam` export set a metadata field to JSON `null` rather than
omitting it — a shape no fixture generated and no test covered. Nothing in the suite could tell us
whether real LSTM exports parse, because no real LSTM export had ever been fed to it.

## Script

1. Obtain LSTM-architecture `.nam` models from a real, public source — actual exports from the NAM
   trainer or a community model site, **not** anything `namir-fixtures` produced.
2. Confirm each declares `"architecture": "LSTM"` (the file is JSON; read it directly).
3. Load each into Namir. Either product shell exercises the parser; the CLAP plugin in a real host
   additionally exercises the plugin path, host-driven block sizes and the sample rate the session
   is running at.
4. Confirm each loads without error — specifically **not** `nam.load.malformed_json` or
   `nam.load.unsupported_architecture`.
5. Play an instrument signal through each. Confirm audible, plausible amp-like output: no silence,
   no noise burst, no dropouts, no crash.
6. Record what was used, so the run is reproducible.

## Executed run — reported by the author, 2026-08-08

Reference LSTM-based `.nam` models were downloaded, loaded into Namir's CLAP plugin under **Reaper**
on Windows, and played through. Reported result: **they worked perfectly, as far as could be told.**

### The model set, examined directly

**Provenance:** downloaded by this repository's author from
[*Towards a (good) CPU-efficient NAM*](https://www.neuralampmodeler.com/post/towards-a-good-cpu-efficient-nam),
posted by Steve (Steven Atkinson, NAM's author) on **2024-03-29**. The post publishes the set to
gather feedback on what compute budgets look like in the low-compute regime — in its own words, to
"understand what typical compute constraints are in this 'low-compute' regime" — and describes them
as supported by the then-current `NeuralAmpModelerCore`.

**The post states no licence or terms for the model files**, and gives no training details (dataset,
input signal, sample rate). The sample rate below is read from the files, not from the post. As with
AQ-4's capture signal, absence of stated terms is not permission: these files are fine to test
against locally and must not be committed to this repository or redistributed — which D-19.1 already
forbids independently, since every fixture in the suite is generated rather than captured.

**Location at the time of writing:** the default library root, `%APPDATA%\Namir\Library`, alongside
248 `.nam` files in total. The 67 LSTM models are trivially identifiable by filename.

**What they are:** a systematic architecture sweep, named `LSTM-<num_layers>-<hidden_size>.nam`.
The filename-to-config mapping was **verified mechanically against all 67 files, with zero
mismatches** — each file's `config.num_layers` and `config.hidden_size` match its own name.

| Field | Value |
|---|---|
| `architecture` | `LSTM` (all 67) |
| `num_layers` | 1, 2, 3, 4 |
| `hidden_size` | 1–12, then 16, 20, 24, 28, 32 |
| `input_size` | 1 (all 67) |
| `version` | 0.5.2 |
| `sample_rate` | 48000 |

The set is complete across that grid except for `LSTM-1-001`, which is absent while `LSTM-2-001`,
`LSTM-3-001` and `LSTM-4-001` are present.

### Consequence for `namir-fixtures`

`LstmShape`'s doc comment carried a standing disclaimer that its three shapes were "not verified
against any real NAM LSTM preset", and invited replacement "if real preset numbers surface later
with a citation". They have now surfaced — and **all three guessed shapes turn out to exist in this
sweep**: `Standard` (2 layers, hidden 32) is `LSTM-2-032`, `Small` (1×16) is `LSTM-1-016`, `Tiny`
(1×4) is `LSTM-1-004`. So the disclaimer is retired and the numbers are unchanged, which is the
better of the two outcomes that comment anticipated.

## Result

**Result: PASS.** For the claim this test exists to check: **real, third-party LSTM `.nam`
exports parse and
run end-to-end through the plugin path in a real host.** That claim had never been tested before this
run, and it is the half of FR-NAM-020 the automated suite structurally cannot reach.

**What this run does *not* establish, stated so nobody reads more into it later:** it is not a
numerical-parity result. This project's standing position (NFR-QUAL-030, D-9.11) is that correctness
for numeric code is never "sounds right" — and the reasoning recorded at R-9 applies with full force
here: a silently-wrong weight order produces a model that loads cleanly, runs at the right cost, and
sounds plausible while being wrong. Listening cannot distinguish that case.

**The source post makes the listening half weaker still, and that is worth stating plainly rather
than leaving for someone to notice later.** It says outright that "some of the models will sound
very different. The intent of this is to focus on compute usage, not sound quality," and separately
that a nano LSTM "often just sounds bad." So this set has *no expectation of good sound to begin
with*: across a sweep whose smallest members are meant to sound poor, "it sounded fine" cannot
distinguish a correct render from an incorrect one, because there is no baseline of what correct is
supposed to sound like here. The run's value is therefore entirely in the load-and-run half — which
is real, and was genuinely untested — and essentially none of it is in the audible half.

The two halves are complementary rather than redundant, and together they leave LSTM in reasonable
shape: the automated test proves the arithmetic against an independent reference but only on shapes
we invented; this run proves real files are accepted and run, but says nothing about the arithmetic.
The residual gap is narrow and now explicit — **no real LSTM model has been compared numerically
against a reference implementation's output.** Closing it needs a reference render of one of these
files, not another listening session.

## Closing the residual gap: numerical parity against the real reference (M10 Phase 4a, 2026-08-09)

This section closes the gap the previous one leaves open. FR-NAM-030 itself (quoted again in full,
since it is what this section verifies): "For each supported architecture, the output of Namir's
inference shall match the reference NAM implementation to within an error whose RMS is at least
90 dB below the RMS of the reference output, over a specified 10-second test signal containing
clean, transient and saturated material." *Verify:* G.

**Why this still can't be a committed automated test.** Same reason as the rest of this file: the
model files this run compares against carry no stated licence and D-19.1 forbids a
captured/licensed asset in the automated suite independently of that anyway. What's new here is the
*reference* side: `NeuralAmpModelerCore`, the actual upstream C++ implementation FR-NAM-030 names,
checked out locally at `C:\namref` and pinned at commit `3cde95c`, built with
`-DNAM_USE_INLINE_GEMM -DNAM_ENABLE_A2_FAST=OFF` (D-9.12's pinned-reference note explains the flag
choice). That build is not part of this repository either, so this comparison can only ever be a
local, human-executed run recorded here — never a CI job.

### Script

1. Build a 10-second, mono, 16-bit-PCM, 48 kHz probe signal containing clean, transient and
   saturated material, per FR-NAM-030's own text: 0-3 s decaying clean tones at six staggered
   fundamentals (82-440 Hz), 3-5 s periodic clicks plus decaying "plucks" at three pitches
   (transient material), 5-10 s a driven tone-plus-noise signal pushed through a `tanh` soft-clip
   (saturated material). Deterministic (seeded xorshift64*), generated by a small standalone Rust
   program written for this run only -- not part of the workspace, not a `namir-fixtures` fixture,
   and not committed, since it exists solely to produce one WAV file for local use.
2. Render each model under test through the pinned reference build:
   `render.exe <model.nam> probe.wav ref_<model>.wav`.
3. Run the new `xtask nam-parity` subcommand (built this milestone,
   `xtask/src/nam_parity.rs`) against the same pair:
   `cargo run --release -p xtask -- nam-parity --model <model.nam> --input probe.wav --reference ref_<model>.wav`.
   It loads `<model.nam>` through `namir_nam::load`, runs `namir-nam`'s own LSTM inference over
   `probe.wav`, and prints the RMS-in-f64, `20 * log10(rms_err / rms_ref)` figure against
   `ref_<model>.wav` -- the same formula
   `crates/namir-nam/tests/fixtures.rs`'s
   `numeric_parity_against_an_independent_reference_implementation` uses, just against the real
   reference render instead of `namir-fixtures`' own port.
4. Repeat across a representative spread of the 67-model grid: at least one model per `num_layers`
   value (1-4), spanning small to large `hidden_size`.

### Executed run — reported by the author, 2026-08-09

Run against 7 of the 67 models, chosen to cover every `num_layers` value and a spread of
`hidden_size` including the smallest, a mid-range, and the largest (`032`) members of the grid --
not an exhaustive run of all 67, but a deliberate spread rather than a cluster. Same provenance and
licence status as the rest of this file: downloaded by this repository's author from the
*Towards a (good) CPU-efficient NAM* post, no stated licence, tested locally only, not
redistributed or committed. Reference build: `NeuralAmpModelerCore` pinned `3cde95c`, built with
`-DNAM_USE_INLINE_GEMM -DNAM_ENABLE_A2_FAST=OFF` at `C:\namref\build_inline`
(`tools\Release\render.exe`). Probe signal: the 10-second clean/transient/saturated WAV described
in the Script above, used identically (bit-for-bit) as the input to both the reference render and
`namir-nam`'s own inference for every model, so the comparison is apples-to-apples per model.

| Model | `num_layers` | `hidden_size` | Measured RMS error vs. reference | Margin below -90 dB floor |
|---|---|---|---|---|
| `LSTM-1-004` | 1 | 4  | -125.02 dB | 35.02 dB |
| `LSTM-1-016` | 1 | 16 | -127.99 dB | 37.99 dB |
| `LSTM-2-008` | 2 | 8  | -130.38 dB | 40.38 dB |
| `LSTM-2-032` | 2 | 32 | -130.25 dB | 40.25 dB |
| `LSTM-3-012` | 3 | 12 | -127.36 dB | 37.36 dB |
| `LSTM-4-001` | 4 | 1  | -114.28 dB | 24.28 dB |
| `LSTM-4-032` | 4 | 32 | -126.66 dB | 36.66 dB |

All seven runs compared exactly 480 000 samples per model (`xtask nam-parity` printed no
sample-rate-mismatch or length-mismatch warning for any of them -- every model, the probe WAV and
every reference render agree at 48 000 Hz and 480 000 samples). Exact figures as printed by
`xtask nam-parity`, e.g. for the first row:

```
nam-parity: <library>\LSTM-1-004.nam vs. <scratch>\ref_LSTM-1-004.wav (480000 samples compared): -125.02 dB (FR-NAM-030 floor: -90 dB)
nam-parity: within FR-NAM-030's -90 dB floor
```

**A judgement call, stated plainly:** seven of the sixty-seven models were run, not all sixty-seven.
The seven were chosen for grid coverage (every `num_layers` value, and `hidden_size` from the
smallest generated shape to the largest) rather than at random, on the reasoning that FR-NAM-030
asks whether Namir's LSTM arithmetic matches the reference implementation -- a question about the
*implementation*, which does not vary per shape the way *cost* does (see the cost curve in
`crates/namir-nam/benches/lstm_inner_loops.rs`, added this same milestone) -- so a spread across the
grid's structural axes is the relevant coverage, not exhaustive enumeration of every hidden-size
value.

### Result

**Result: PASS.** For the claim this section exists to check: **for the seven real LSTM models
tested,
spanning `num_layers` 1-4 and a spread of `hidden_size`, `namir-nam`'s LSTM inference matches
`NeuralAmpModelerCore`'s own reference render to well inside FR-NAM-030's -90 dB floor** -- the
worst of the seven margins is still 24.28 dB of headroom (`LSTM-4-001`), and the rest cluster
between 35 and 41 dB below the floor. Combined with the automated `trace-partial:` evidence already
in `crates/namir-nam/tests/lstm_fixtures.rs` (parity against `namir-fixtures`' own independent
port, on generated shapes, with a short probe signal), **FR-NAM-030 is now met for LSTM on both of
the clauses M10 Phase 4 identified as open**: comparison against the actual reference
implementation the requirement names, and real (not generated) model weights.

**What this run does *not* establish, stated so nobody reads more into it later.** It does not
establish parity for the other 60 models in the set, or for any LSTM shape outside this specific
67-model grid -- `hidden_size`/`num_layers` combinations the sweep never published are simply
untested. It says nothing about WaveNet or A2, whose own half of this same requirement is being
closed separately and is not this section's concern. It does not establish that the probe signal
built for this run is *the* canonical FR-NAM-030 signal -- the requirement specifies clean,
transient and saturated *content*, not a byte-exact waveform, and this run's signal is one
reasonable construction of that, documented in full in the Script above rather than asserted
without detail. And, as the file's existing text already says of the earlier listening run, this
result is about **arithmetic**, not about tone: a numerically-accurate render of a model that
"often just sounds bad" (the source post's own words) still sounds bad, and this section makes no
claim to the contrary.
